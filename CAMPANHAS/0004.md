# Campanha 0004 — Persistência SQLite interna

## Escopo e resultado

Implementação da infraestrutura mínima e isolada de persistência interna prevista em `IDB-FREEZE-AUTH-v5.6`. Resultado técnico: **PARTIAL**. A API integrada foi comprovada em Termux Android ARM64 e os testes passaram; o uso de `node:sqlite` continua classificado pelo Node como Release Candidate, e o `npm ci` reportou nove vulnerabilidades moderadas no conjunto de dependências do projeto. O resultado de conformidade da execução é **FAIL**: por erro operacional, o commit local de código foi enviado ao remoto do repositório principal, contrariando a proibição expressa de push. O incidente foi verificado e documentado; nenhuma tentativa de apagar/regravar o remoto foi feita.

O SQLite interno guarda apenas metadados mínimos de instalação para provar a infraestrutura. Não implementa perfis externos, cofre, histórico de consultas ou funcionalidades posteriores. Nenhuma conexão com o banco interno é exposta como API SQL. O SQLite externo permanece responsabilidade futura e separado.

## Decisão do driver

Selecionado o módulo integrado `node:sqlite` (`DatabaseSync`), sem dependência SQLite npm nativa. A prova real em Node `v26.4.0`, Android `arm64`, SQLite embutido `3.53.4` demonstrou abertura de arquivo, WAL efetivo, foreign keys efetivas, rollback, reabertura, `integrity_check`, `foreign_key_check` e permissões 0700/0600. Ver `EVIDENCIAS/0004/DECISAO-DRIVER.md` e `driver-probe.mjs`.

A decisão evita compilar addon nativo no Termux e passa a exigir Node `^22.13.0 || ^24.0.0 || >=26.0.0`. Limitações: a API está em estabilidade 1.2 (Release Candidate), é síncrona e pode bloquear o event loop em operações longas; não existe prova nesta campanha para Node 22/24 no Android. `better-sqlite3` não foi instalado, pois não foi comprovada distribuição Android/Bionic compatível. `node-sqlite3` não foi selecionado (projeto arquivado, sem suporte Android documentado).

## Implementação

Novo workspace `packages/persistence` com caminho privado absoluto, permissões restritas, proteção contra componentes simbólicos, conexão interna encapsulada, PRAGMAs configurados e verificados, integridade, ledger de migrações determinísticas com checksums, rollback, schema futuro/incompatível preservado, coordenador serial de escrita com transações `BEGIN IMMEDIATE`, cancelamento antes do commit, pausa após resultado de commit incerto e fechamento/checkpoint. Fastify abre a store na inicialização e fecha-a no encerramento.

O schema atual é deliberadamente mínimo. Não há SQL arbitrário na API pública. Não há retry automático após `COMMIT_OUTCOME_UNKNOWN`.

## Verificações reproduzíveis

Ambiente observado: Termux Android ARM64; Node `v26.4.0`; npm `11.21.1`; SQLite embutido no Node `3.53.4`; SQLite CLI `3.54.1` (não usado pela aplicação); Clang `21.1.8`; Git `2.56`. A evidência detalhada e comandos estão em `EVIDENCIAS/0004/RESULTADOS.md`.

- `npm ci --fetch-retries=0 --fetch-timeout=120000`: exit 0; adicionou 192 pacotes; auditoria do npm reportou 9 vulnerabilidades moderadas. Não foi executado `npm audit fix`.
- `npm run verify`: build, typecheck, lint e Vitest concluídos com exit 0; 6 arquivos de teste e 22 testes aprovados.
- A suíte usa SQLite real para abertura/criação, reabertura, migrações múltiplas e falhas, checksums, integridade, WAL/FK, concorrência/serialização, rollback, cancelamento, busy timeout, fechamento, banco futuro/corrompido preservado, interrupção SIGKILL simulada em transação e isolamento de arquivo externo.
- Prova independente do driver: `node EVIDENCIAS/0004/driver-probe.mjs` (ver saída registrada em `RESULTADOS.md`).
- `git diff --check`: exit 0.

## Riscos e pendências

1. Decidir se `node:sqlite` Release Candidate é aceitável para a primeira distribuição; alternativa requer prova real no Termux antes de adoção.
2. Avaliar as nove vulnerabilidades moderadas reportadas por `npm ci` em trabalho de segurança próprio, sem atualizações nesta campanha.
3. Homologar versões mínimas oficialmente suportadas e persistência em diferentes versões Android/Termux.
4. O coordenador atual executa callbacks síncronos; operações longas devem permanecer fora do escopo de escrita de metadados ou ser avaliadas antes de introduzir workers.
